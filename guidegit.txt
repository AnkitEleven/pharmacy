1. CORE CONCEPTS: THE 3 STAGES OF GIT
================================================================================

Git doesn't just take files and upload them. It tracks files in 3 main stages:

   Working Directory  ----[ git add ]---->  Staging Area  ----[ git commit ]---->  Local Repository (.git)
   (Files you edit)                       (What will be saved)                   (Saved history snapshot)
                                                                                            |
                                                                                    [ git push ]
                                                                                            v
                                                                                    Remote Repository (GitHub)

- Working Directory: Your active folder on your computer where you edit code/images.
- Staging Area (Index): A waiting room where you prepare the exact files you want in your next commit.
- Local Repository: Your permanent commit history on your local machine.
- Remote (GitHub): The shared online copy where team members pull and push.

2. BASIC EVERYDAY WORKFLOW (SINGLE PERSON)
================================================================================

Step 1: Check what you modified
   git status

Step 2: Review exact line changes
   git diff                     # Shows changes not yet staged
   git diff --staged            # Shows changes staged for commit

Step 3: Stage your changes
   git add filename.html        # Stage a specific file
   git add .                    # Stage all changes in current folder

Step 4: Commit with a meaningful message
   git commit -m "Update hero section headline and admissions form button"

Step 5: Push to GitHub
   git push origin main         # or whatever branch you are on

3. PARTIAL COMMITS VS. FULL COMMITS
================================================================================

A) HOW TO COMMIT EVERYTHING (FULL COMMIT):
   Use this when you want all new files, deleted files, and modified files committed together.

   Command:
   git add -A                   # Adds ALL additions, modifications, and deletions
   git commit -m "feat: complete pharmacy faculty section and update layout"
   git push origin <branch-name>

   Shortcut for modified/deleted files already tracked by Git:
   git commit -am "fix: correct typo in hero copy"
   *(Note: -am does NOT include brand new untracked files)*

B) HOW TO COMMIT SPECIFIC FILES (PARTIAL COMMIT):
   Use this when you worked on 5 files, but only 2 of them are ready to be saved.

   Command:
   git status                   # See the list of changed files
   git add index.html           # Stage only index.html
   git add images/logo.png      # Stage only logo.png
   git commit -m "refactor: update logo and index markup"
   # The remaining files stay untouched in your working directory!

C) HOW TO COMMIT ONLY CERTAIN PARTS OF A SINGLE FILE (INTERACTIVE / PATCH):
   Use this when you made 2 different features inside the same file (e.g. index.html)
   and want to split them into separate clean commits.

   Command:
   git add -p index.html
   # Git will show each block of change (hunk) and ask:
   # y = stage this block
   # n = do not stage this block
   # s = split this block into smaller pieces
   # q = quit

4. UNDOING MISTAKES SAFELY
================================================================================

Scenario 1: You modified a file but want to discard changes and restore original:
   git restore index.html

Scenario 2: You ran `git add .` by mistake and want to unstage files:
   git restore --staged index.html     # Unstages index.html (keeps your edits)
   git restore --staged .              # Unstages all files

Scenario 3: You want to change the last commit message before pushing:
   git commit --amend -m "New better commit message"

Scenario 4: You committed already, but haven't pushed, and want to undo the commit:
   git reset --soft HEAD~1      # Undoes the commit, leaves all changes staged
   git reset --mixed HEAD~1     # Undoes the commit, leaves changes in working folder
   git reset --hard HEAD~1      # DANGER: Deletes commit and all changes completely!

Scenario 5: You already pushed to GitHub and need to undo a bad commit safely:
   git revert <commit-id>       # Creates a new commit that cancels out the old commit
   git push origin main

5. BRANCHING STRATEGY (ISOLATION)
================================================================================

NEVER work directly on `main` when working in a team or doing major changes!
Always create a feature branch.

1. Create and switch to a new branch:
   git checkout -b feature/faculty-slider
   # Modern syntax:
   git switch -c feature/faculty-slider

2. Check which branch you are on:
   git branch

3. Work, make commits on your branch:
   git add .
   git commit -m "feat: implement 3D coverflow for faculty profiles"

4. Push your branch to GitHub:
   git push -u origin feature/faculty-slider

5. Switch back to main:
   git switch main

6. MULTI-PERSON TEAM WORKFLOW (THE INDUSTRY STANDARD)
================================================================================

When 3, 5, or 20 developers work on the same project:

----------------------------------------------------------------------
A) THE GOLDEN RULE OF WORKING WITH OTHERS:
   ALWAYS PULL BEFORE YOU START WORKING & BEFORE YOU PUSH!
----------------------------------------------------------------------

DAILY CYCLE FOR EACH DEVELOPER:

Step 1: Start your day by updating your local `main` branch:
   git switch main
   git pull origin main

Step 2: Create a branch for your assigned task:
   git switch -c feature/add-pharmacovigilance-workshop

Step 3: Do your work and commit frequently in small chunks:
   git add images/workshop.jpg
   git commit -m "feat: add workshop banner image"
   git add index.html
   git commit -m "feat: link workshop image in events section"

Step 4: While you were working, a teammate might have pushed code to `main`.
        Re-sync your branch with the latest changes from `main`:
   git fetch origin
   git rebase origin/main
   # (If there are conflicts, see section 7 below)

Step 5: Push your branch to GitHub:
   git push -u origin feature/add-pharmacovigilance-workshop

Step 6: Open a Pull Request (PR) on GitHub:
   - Go to GitHub -> Pull Requests -> "New pull request".
   - Your teammates review your code.
   - Once approved, merge it into `main` using GitHub's "Merge pull request" button.

Step 7: Clean up after merge:
   git switch main
   git pull origin main
   git branch -d feature/add-pharmacovigilance-workshop

7. HANDLING MERGE CONFLICTS STEP-BY-STEP
================================================================================

What is a Conflict?
A conflict happens when Developer A and Developer B edit the EXACT SAME LINES
of the same file, and Git cannot automatically decide whose code to keep.

WHEN A CONFLICT HAPPENS, GIT PRINTS:
   CONFLICT (content): Merge conflict in index.html
   Automatic merge failed; fix conflicts and then commit the result.

HOW TO SOLVE IT:

Step 1: Find out which files have conflicts:
   git status
   # Conflicted files will appear under "both modified:"

Step 2: Open the conflicted file in VS Code or any editor.
        Git marks the conflict like this:

   <<<<<<< HEAD (Your changes)
   <h2 class="title">Welcome to NIMS Institute of Pharmacy</h2>
   =======
   <h2 class="title">NIMS University - Department of Pharmaceutical Sciences</h2>
   >>>>>>> main (Teammate's incoming changes)

Step 3: Decide what to keep:
   - Option A: Accept Current Change (Keep your code)
   - Option B: Accept Incoming Change (Keep your teammate's code)
   - Option C: Combine both manually!

   In your editor, remove the conflict markers:
   Delete: `<<<<<<< HEAD`
   Delete: `=======`
   Delete: `>>>>>>> main`
   Leave only the final clean code you want!

Step 4: Save the file and tell Git the conflict is resolved:
   git add index.html

Step 5: Finish the merge or rebase:
   If you were doing a merge:
      git commit -m "merge: resolve conflict in index.html heading"
   If you were doing a rebase:
      git rebase --continue

Step 6: Push to GitHub:
   git push origin <your-branch>

8. GIT STASH: PAUSING UNFINISHED WORK
================================================================================

Scenario: You are in the middle of editing 10 files, code is half-broken, and
suddenly your manager says: "Fix an urgent bug in production right now!"

You cannot commit half-broken code. What do you do?

Step 1: Save your current work to a temporary clipboard:
   git stash -u                 # -u includes untracked files

Step 2: Your working directory is now 100% clean!
   git switch main
   git pull origin main
   # Fix the urgent bug
   git add .
   git commit -m "fix: resolve urgent header alignment"
   git push origin main

Step 3: Switch back to your feature and bring back your paused work:
   git switch feature/my-work
   git stash pop                # Restores your exact half-finished work!

Useful Stash Commands:
   git stash list               # View all saved stashes
   git stash drop               # Discard the saved stash if no longer needed

9. ADVANCED GIT TECHNIQUES
================================================================================

A) CHERRY-PICKING (Grab 1 specific commit from another branch):
   Suppose someone wrote a great bugfix in branch `experiment` with commit hash `a1b2c3d`.
   You want ONLY that fix in your branch without merging everything else:
   git switch feature/my-branch
   git cherry-pick a1b2c3d

B) GIT LOG WITH PRETTY GRAPH:
   See branch visually in terminal:
   git log --oneline --graph --decorate --all -15

C) CLEANING UNTRACKED JUNK FILES:
   git clean -fdn               # Dry run: shows what files would be deleted
   git clean -fd                # Deletes untracked temporary files and folders

D) TAGGING RELEASES:
   git tag -a v1.0.0 -m "Release v1.0.0 of Pharmacy landing page"
   git push origin v1.0.0

10. RECOMMENDED TEAM RULES & BEST PRACTICES
================================================================================

1. Use a strict `.gitignore` file:
   Never commit node_modules, .DS_Store, editor caches, OS junk or zip files.
   Typical entries:
      node_modules/
      .env
      .vscode/
      *.tmp
      *.log
      scratch/

2. Write Conventional Commit Messages:
   Use standard prefixes so everyone knows what the commit did:
      feat:     A new feature (e.g. `feat: add 3D facilities slider`)
      fix:      A bug fix (e.g. `fix: prevent JS crash on missing hero element`)
      style:    CSS or design changes (e.g. `style: adjust card padding`)
      refactor: Code restructuring without changing functionality
      docs:     Documentation updates (e.g. `docs: add git guide`)
      chore:    Maintenance tasks (e.g. `chore: update dependencies`)

3. Never use `git push --force` on shared branches (`main` or `develop`).
   Force pushing overwrites other people's commits!
